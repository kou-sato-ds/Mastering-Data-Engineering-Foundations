## 1. Spark Tuning：メモリ管理の「聖域」と「共有エリア」
### 🐎 たとえ：巨大な厩舎（きゅうしゃ）の運用
[Spark Tuning Guide](https://spark.apache.org/docs/latest/tuning.html)に基づき、限られた計算リソースを最適化する戦略を整理しました。

*   **予約席 (40% + 300MiB)**: システム維持・緊急時用のバッファ。
*   **活動エリア M (60%)**: `spark.memory.fraction`。実際にタスクが動く広さ。
*   **キャッシュ聖域 R (Mの50% = 全体の30%)**: `spark.memory.storageFraction`。再利用するデータを保護する領域。

> **学びの足跡:** 
> 計算エリアが足りない時は保存エリアから借りるが、最低限のR（30%）だけは死守されるという「柔軟性と規律」の設計思想をコードに反映しました。

## 2. データの「事前検診」：SizeEstimator
### 🐎 たとえ：レース前の馬体重測定
メモリ破綻（OOM）を防ぐため、実行前にオブジェクトサイズを推測する「防衛運転」の実装です。

*   **実装内容**: `SizeEstimator.estimate()` を活用。
*   **実務への応用**: 
    大規模な工数分析データを読み込む前にサイズを把握し、事前に処理ルート（パーティション数等）を動的に変更するロジックの基礎を磨きました。

## 3. 並列化の黄金比
### 🐎 たとえ：1頭で走るより、みんなで分担！
1つのコア（作業員）に無理をさせず、タスクを最適に分散させる戦略です。

*   **黄金比**: 1コアあたり2〜3タスクの割り当て。
*   **実装内容**: `spark.default.parallelism` をコア数に比例設定。
*   **実務への応用**: 日付別フォルダに分散したデータの探索時間を、並列スレッド調整により劇的に短縮する手法を記録。

## 4. 実装の「型」：Stratified K-fold パイプライン
### 🐎 たとえ：5つのチームで交代制テスト！
どんなデータが来ても揺るがない評価を行うための、汎用テンプレートを構築しました。

*   **層化分割 (Stratified)**: ターゲット変数の比率を維持し、公平な5分割を実現。
*   **実装のこだわり**: LightGBMやPyTorch等、異なるエンジンに即座に載せ替え可能な「外枠」を、何も見ずに書けるまで徹底的に写経。

## 6. 統計的アプローチによる欠損値補完（Imputation Strategy）
### 🧪 たとえ：パズルの修復師
統計検定2級の知見を活かし、データの穴を「根拠を持って」埋めるロジックを実装しました。

*   **平均値 vs 中央値**: 外れ値（例：所得10,000）の影響を受けやすい平均値ではなく、ロバストな「中央値」を選択する妥当性を検証。
*   **グループ別補完**: `department` ごとの特性に応じた補完を行うことで、ドメイン知識を反映した精度の高い前処理を実現。

> **学びの足跡:** 
> 統計的な「代表値の性質」を理解し、実務上の「データの歪み」に対する具体的な解決策として実装に落とし込みました。

## 7. フィーチャースケーリングの「型」（Feature Scaling）
### 🧪 たとえ：異なる競技のスコアを「偏差値」で比べる
単位（円、歳、個数など）がバラバラなデータを、AIが公平に評価できるように「物差し」を揃えるロジックを実装。

*   **StandardScaler（標準化）**: 
    統計検定2級の最重要テーマ「Z変換」を適用。平均0、標準偏差1に変換し、外れ値が存在するデータでも安定した学習を可能にします。
*   **MinMaxScaler（正規化）**: 
    データを0〜1の範囲にスケーリング。特定の範囲内に収める必要があるアルゴリズム（ニューラルネットワーク等）への対応力を習得。
*   **実務の鉄則「Data Leakage」防止**: 
    テストデータに対して `fit` を行わず、訓練データの統計量のみで `transform` する「防衛的な実装」を徹底。

> **学びの足跡:** 
> 統計理論としての「標準正規分布」と、ライブラリとしての「Scikit-learn」を接続。単にツールを使うだけでなく、内部で行われている計算（平均引き、標準偏差割り）の数学的背景を意識したコーディングを実現しました。

## 8. カテゴリ変数のエンコーディング（Categorical Encoding）
### 🧪 たとえ：言葉の壁を越える「翻訳機」
AIが直接理解できない「文字情報（部署名や役職）」を、意味を保ったまま「数字」へ変換。

* **One-Hot Encoding**: 
    部署名のように「順序がない」データに使用。`drop_first=True` を設定することで、多重共線性（マルチコ）を回避し、行列計算の安定性を高める「実務の作法」を実装。
* **Label Encoding**: 
    各要素に一意の数値を割り当て。主にターゲット変数や、木モデルベースのアルゴリズムで使用。
* **Ordinal Encoding**: 
    役職（Junior < Manager）のように「順序に意味がある」場合、手動マッピングによりデータの「重み」を正しく表現。

> **学びの足跡:** > データの背景（ドメイン知識）に合わせて「順序の有無」を判断し、最適な変換手法を選択する重要性を習得。G検定でも頻出の「多重共線性」への対策をコードレベルで定着させました。
